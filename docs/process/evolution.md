# 规范生长与迭代机制（Evolution）

> **版本**：v0.1
> **变更记录**：v0.1 初稿（2026-08-15，用户要求：已有规范在必要阶段需要生长或迭代）

## 1. 理念

- **规范是活的**：项目前进，规范随之生长；但生长必须有仪式——可追溯、可回退、不随性
- **文档即真相源**：事实以文档为准。文档没有的，**先长文档、再改实现**；文档过时的，走生长流程更新，而不是让实现悄悄偏离
- 生长示例：暗色主题就是由亮色规范生长而来（design-language.md §2.5，来源可追溯）

## 2. 生长触发条件

1. 实现中发现规范未覆盖的空白（新组件、新交互模式、新状态）
2. 规范与实现发生冲突
3. 用户提出新要求
4. 里程碑回顾发现规范过时（见 process/README.md §9 回顾点）
5. 任何一次"规范没挡住问题"的事故

## 3. 生长流程（五步）

1. **提案**：在相关文档或新 ADR 中写明"现状 — 问题 — 提案"，标注「提案」+ 日期。**不得直接改正文定论**
2. **确认**：宪法级文档（design-language.md、AGENTS.md、影响全仓库的 process 条款）必须用户确认；次级文档可由项目主会话在明确授权下确认
3. **落档**：升版本号，写变更记录（版本 | 日期 | 摘要 | 触发来源）
4. **实施**：按新规范同步修改实现
5. **回查**：实施后逐条对照文档核对，消除"两张皮"；回查结果记入提交说明或汇报

> 快速通道：纯笔误/格式修正可不走完整流程，但必须在变更记录中注明"勘误"。

## 4. ADR 生命周期

- 状态机：`proposed`（提案）→ `accepted`（接受）→ `superseded`（被新 ADR 推翻，须注明新 ADR 编号）
- 架构级决策**必须**落 ADR（索引与模板见 `docs/architecture/adr/README.md`）
- 变更架构 = 写新 ADR，旧 ADR 标 superseded；禁止静默改架构

## 5. 反幻觉在生长中的落地

- 提案必须给出证据/出处；无法溯源的"感觉"不得进文档
- 文档中的每个"决定"都要能指向：用户指令 / 已有文档 / 明确标注的推断
- 生长出的新内容必须写明**推导规则**（例：暗色令牌表的"来源"列、本机制中的五步流程）
- 规范之间不得互相矛盾：发现矛盾 → 先提提案解决矛盾，再动手实施

## 6. 版本号规则

- 文档版本 `v主.次`：每次生长升"次"；方向性推翻升"主"
- 变更记录表放文首：`版本 | 日期 | 变更摘要 | 触发来源`
- 引用其他文档时尽量带版本号（如 `design-language.md v0.2 §2.5`），避免歧义
