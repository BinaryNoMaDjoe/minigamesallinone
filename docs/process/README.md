## 1. 核心纪律（反幻觉）

1. **事实必须有出处**：仓库文档 > 用户明确指令 > 明确标注的"推断/待确认"。禁止把猜测、印象、网上印象当事实写入代码或文档。
2. **文档即真相源**：一切以 `docs/` 为准；代码与文档冲突时以文档为准回查，确需变更走生长流程。
3. **未确认 = 待定**：任何未拍板的选项只能以「待定/提案」形式存在，不得当作已定执行。
4. **验证优先**：宣称完成前必须通过验证（typecheck / build 等），禁止"应该没问题"。
5. **范围纪律**：只做要求的事；超出范围先问。

> 以上五条与 `AGENTS.md` 红线一致，对**人与 AI 会话同等适用**。

## 2. Git 工作流

- 主分支 `main` 永远可构建、可发布
- 单人开发以短分支或小步直接提交为主；**每个新游戏 = 独立提交序列**，方便回滚与追溯
- 分支命名：`feat/<主题>`、`fix/<主题>`、`docs/<主题>`、`chore/<主题>`（如 `feat/snake`）
- 合并策略：线性历史优先（rebase / squash 视阶段需要），禁止 `--no-verify` 绕过质量门

## 3. Commit 规范

- 格式：**Conventional Commits**，描述用**中文**：
  `type(scope): 中文描述`
- `type`：`feat` `fix` `docs` `chore` `refactor` `style` `perf`
- `scope`（本仓库约定）：`design` `process` `architecture` `agents` `scaffold` `theme` `ui` `i18n` `games` `services` `deps` `license`
- **拆分原则**：一次提交只做一类事——文档与代码分开、不同游戏分开、规范修订与实施分开
- 示例：
  - `docs(design): 美术设计语言规范 v0.2 与溯源素材`
  - `feat(games): 新增贪吃蛇`
  - `chore(scaffold): 初始化 Vite + React + TypeScript 骨架`
  - `docs(process): 流程规范生长至 v0.2`
- 禁止：大杂烩提交、空描述、中英混排、无 scope 的随意信息

## 4. 质量门

- `husky + lint-staged`：提交前自动跑 ESLint + Prettier（脚手架阶段落地，落地前手动执行等效命令）
- TypeScript 严格模式：`typecheck` + `build` 通过才可提交
- 首版**不做**自动化测试（决策记录 #12）；**CI 与自动部署默认禁止**，仅在用户明确人工命令时才能搭建/执行（决策记录 #16）
- 代码审查：提交前按 `skills/skill-code-review.md` 自检；结构性变更（壳层、令牌、接口）建议开 `reviewer` 代理互审

## 5. 版本与发布

- 产品版本 SemVer，首版 `v0.1.0`
- 发布 = `build` 产物（纯静态），Changelog 由规范化 commit 自动生成；**发布与部署动作默认禁止，必须由用户人工命令发起**（决策记录 #16）
- 文档版本独立于产品版本：`v主.次`（次 = 生长次数），重大推翻升主版本
- 每个规范文档文首必须有：版本号 + 变更记录（版本 | 日期 | 摘要 | 触发来源）

## 6. 文档纪律

| 文档 | 地位 | 修改要求 |
|---|---|---|
| `docs/design-language.md` | **宪法级** | 必须用户确认 + 升版本 + 变更记录 |
| `AGENTS.md` | 宪法级 | 必须用户确认 + 变更记录 |
| `docs/process/` | 强制 | 走生长流程；影响全仓库纪律的条款需用户确认 |
| `docs/architecture/` 与 ADR | 强制 | ADR 生命周期见 `evolution.md`；推翻旧 ADR 必须新 ADR 标注 superseded |
| `docs/design-reference/` | 只读素材 | 禁止修改 |
| `skills/` `agents/` | 工具性 | 可随项目生长，修订需更新版本与变更记录 |

- **规范即代码**：令牌键名、组件规格在文档与代码中一一对应，杜绝"两张皮"
- 决策记录**唯一主表**在本文档 §8（`docs/design-language.md` §14 为其子集快照，以主表为准）

## 9. 回顾点（Review Checkpoints）

- **每个游戏完成时**：回看 skill-add-game 是否有需要生长的步骤
- **每个里程碑（首版可发布 / 接后端前 / 接入真实域名前）**：回看全部规范是否过时、是否有"两张皮"
- **任何一次"规范没挡住问题"的事故**：立即启动生长流程修订对应规范，而不是只修个案
